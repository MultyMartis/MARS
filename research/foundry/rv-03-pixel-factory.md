# REPORT — RV-03 PIXEL FACTORY & AI PRODUCTION RESEARCH

## Executive Summary

Мировая практика уже не сводится к одной магической операции «PNG/FIGMA → production-ready HTML». Реально работающие системы делятся на два класса. Первый — **structure-first**: они сначала берут структурированные данные из Figma, дизайн-системы и компонентного слоя, а уже потом генерируют код. Второй — **vision-first**: они стартуют со скриншота, эскиза или изображения, строят промежуточное представление layout/элементов и только затем собирают HTML/CSS. Исследования Design2Code, WebSight, LayoutCoder и UI2Code^N показывают, что у one-shot screenshot-to-code систем основные провалы — это извлечение визуальных элементов, корректная раскладка и устойчивое доведение рендера до эталона, поэтому лучшие современные пайплайны стали итеративными: render → diff → refine, а не одноразовыми. citeturn12view0turn12view4turn12view5turn12view6

Если смотреть именно на коммерческие инструменты, то Builder Visual Copilot, Locofy и Anima — это в первую очередь **Figma-grounded production accelerators**: они опираются на структуру файла, component mapping, responsive metadata и ручную/полуавтоматическую настройку. Galileo в его текущем публичном виде фактически представлен через Google Stitch и относится скорее к **prompt/image-to-UI + export** инструментам, чем к строгому pixel-perfect Figma-to-code конвейеру. v0 и Lovable — это уже **agentic code generation systems**: они могут брать Figma, изображения, промпты и существующий код, но их реальная сила — не в «точном копировании макета», а в более широком цикле генерации, доработки, синка с репозиторием и автоисправления. citeturn11view0turn11view1turn11view3turn20view0turn20view1turn11view4turn19view3turn11view5

Для Pixel Factory это означает главное: **ядром системы должен быть не один генератор, а оркестратор пайплайна**. На практике нужно отдельно держать слой структурной экстракции, слой component/design-system matching, слой генерации, слой рендера, слой visual diff и слой approval. Именно эта связка, а не отдельная LLM, сегодня соответствует мировому рабочему стандарту. Инструменты QA это подтверждают: Playwright, BackstopJS, Percy и Chromatic все построены вокруг baseline-снимков, повторяемого рендера, сравнения изменений и human review/approval. citeturn11view7turn11view8turn11view9turn11view10turn11view19

Поэтому для WF-A03 логика такая: если задача — **production-grade pixel-perfect frontend**, то целевой контур должен быть не «еще один generator», а **Foundry Pixel Factory** как замкнутый цикл: ingest → extract → map → generate → render → diff → auto-fix → approve → merge. Это намного ближе к тому, как реально работают современные системы, и лучше объясняет, где нужен человек, где допустима автоматизация, а где нужна deterministic logic вместо LLM-only подхода. citeturn12view5turn19view4turn11view18turn11view19

## Figma To Code Systems

В мировой практике Figma-to-code-инструменты различаются не по маркетинговой вывеске, а по тому, **на что они опираются как на ground truth**. Builder Visual Copilot и Locofy стараются связать дизайн с уже существующим кодом и дизайн-системой. Anima делает упор на responsive code из Figma Dev Mode и подготовленные breakpoints/auto-layout. Stitch, v0 и Lovable сильнее в генеративной части и быстрее на этапе exploration, но слабее как strict pixel-fidelity engine без дополнительной валидации и ручной коррекции. citeturn11view0turn11view2turn11view3turn20view0turn19view3turn11view5

**Builder.io Visual Copilot** — один из самых зрелых вариантов именно для production handoff. Его базовый принцип — не просто превратить Figma в JSX/HTML, а **сопоставить Figma-компоненты с реальными компонентами из кодовой базы**. Builder прямо пишет про AI semantic matching для component mapping, использование существующих компонентов и CLI, который интегрирует Figma-дизайны прямо в кодовую базу. Это важный маркер зрелости: система не старается заново придумать Button/Card/Modal, а пытается использовать уже существующие implementation units. Для Pixel Factory это эталонный паттерн. citeturn11view0turn11view1turn19view0turn19view1turn19view2

**Locofy** работает иначе: у него сильная ставка на **semantic tagging и design-time annotation**. В classic flow ключевой шаг — tagging interactive elements; файл не должен быть просто картинкой, дизайнер или команда должны пометить, что является button, input, drawer, image и так далее. У Locofy есть auto-tagging by layer names, AI-assisted tagging, интерактивный preview во время tagging, live responsive prototypes, а в CLI/MCP-линейке — mapping Figma components на реальные code components через `locofy.config.json`, `locofy push` и plugin-side mapping. Это делает Locofy ближе к полуавтоматическому production compiler, чем к прямому one-shot generator. citeturn15search5turn15search6turn15search1turn15search0turn15search2turn16search1turn16search6turn16search13

**Anima** занимает позицию между handoff и code export. В Figma Dev Mode Anima генерирует clean, responsive code в React/Vue/HTML и разные стили CSS/SCSS/Tailwind/Styled Components. При этом их документация явно показывает зависимость качества от правильной подготовки макета: breakpoints, auto-layout, responsive behavior. То есть Anima хорошо работает там, где дизайн уже сравнительно дисциплинирован и adaptability описана на уровне Figma-свойств. Это не vision-only система; она гораздо успешнее на структурированном design input, чем на свободном PNG. citeturn11view3turn4search1turn4search9turn13view7

**Galileo** как тема из брифа сегодня практически нужно рассматривать через **Google Stitch**. Публичные материалы Google описывают Stitch как систему, которая преобразует text/image inputs в UI designs и frontend code, умеет refinement через chat, paste to Figma, voice-based iteration, import/export design rules через DESIGN.md и экспорт в developer tools. Это уже не классический Figma-to-code, а **generative design-to-code canvas**, где design system context и iterative steering важнее прямой deterministic трансляции. Для Foundry такой класс систем полезен как upstream ideation/generation layer, но не как финальный source of truth для pixel-perfect shipping. citeturn20view0turn20view1turn20view2turn20view3turn20view4

**v0** от Vercel — это agentic UI/code system, а не просто Figma exporter. Vercel пишет, что v0 умеет импортировать Figma, вытаскивать context из файлов и дополнительных visuals, а также работать на существующих codebases через sandbox runtime, где каждый prompt живет прямо в repo. Дополнительно Vercel раскрывает, что надежность обеспечивается не одной генерацией, а multi-step agentic pipeline с dynamic prompt layer и deterministic/model-driven autofixers. В контексте Pixel Factory это сильный ориентир: production-ready workflow строится вокруг repo grounding и repair loop, а не только вокруг design parsing. citeturn11view4turn19view3turn19view4turn17search9

**Lovable** — еще дальше от строгого Figma-to-code и ближе к «AI software engineer» для full-stack web apps. Но для этого исследования он важен потому, что показывает зрелую модель **human-guided visual editing**: preview toolbar, element selection, draw annotation, inline text edit, image replacement, GitHub two-way sync, branch operations, PR creation и встроенный “Try to Fix” по логам. То есть Lovable полезен не как deterministic extractor, а как пример того, как современные системы встраивают человека прямо в visual correction loop. citeturn11view5turn19view5turn19view6turn19view7turn19view8

Практический вывод по Part 1 такой. **Builder / Locofy / Anima** — это инструменты, которые ближе всего к инженерной части Figma-to-production. **Stitch / v0 / Lovable** — это генеративные и агентные системы, сильные в ideation, scaffold, refinement и repo workflows. Если цель WF-A03 — именно Pixel Factory, основной ориентир должен быть на первый класс плюс проверочный контур из второго. citeturn11view0turn16search6turn11view3turn20view0turn19view3turn11view5

## Extraction Systems

Современная design extraction практика строится вокруг четырех типов извлечения: **structure extraction, component extraction, instance extraction, asset extraction**. В Figma-ориентированных системах это почти всегда делается через дерево nodes, типы узлов, metadata о компонентах и экспорт изображений/векторов. В vision-first системах, где на входе PNG или screenshot, те же сущности восстанавливаются уже через layout parsing, element relation construction и промежуточные layout trees. Именно поэтому PNG→HTML почти всегда менее надежен, чем FIGMA→HTML: ему приходится сначала угадать структуру, а не взять ее из источника. citeturn13view3turn11view15turn11view16turn11view17turn11view14turn12view6

**Structure extraction** в Figma-мире начинается с дерева документа: file endpoints возвращают JSON файла, а `document` содержит node tree. Node types задают типы объектов — FRAME, GROUP, TEXT, COMPONENT, INSTANCE и так далее. На этом строится нормализация в промежуточное представление: frame hierarchy, auto-layout relations, absolute positioning, spacing, alignment, typography tokens, fill/stroke/effect metadata. В vision-first research аналогом этого слоя выступают layout parsers. LayoutCoder прямо разбивает задачу на element relation construction, UI layout parsing и layout-guided code fusion, то есть сначала восстанавливает структуру и отношения, а потом генерирует код. citeturn13view3turn11view15turn13view7turn11view14turn12view6

**Component extraction** — это извлечение reusable units и их свойств. В Figma это поддерживается как на уровне `COMPONENT`, так и через published components/styles metadata. Для production systems это критично, потому что компонент — не просто визуальная группа, а **единица соответствия между design system и code system**. Builder строит вокруг этого component mapping к реальным компонентам репозитория. Locofy формализует тот же паттерн через mapping на custom code components и manual prop mapping. Поэтому зрелая Pixel Factory не должна напрямую генерировать div soup; она должна сначала решить, какой кусок макета является existing component, а что требует нового кода. citeturn13view1turn11view16turn11view0turn19view1turn16search1turn16search6

**Instance extraction** — это извлечение конкретных применений компонента, их overrides и variant state. Документация Figma определяет `InstanceNode` как копию компонента, автоматически обновляемую при изменении компонента, а `ComponentNode` умеет создавать инстансы и возвращать список инстансов документа. Для production это означает, что Pixel Factory должна различать **component definition** и **instance realization**. Ошибка этого уровня приводит к типовой проблеме, когда система правильно распознает “это карточка”, но теряет конкретный текст, image swap, variant, badge state или nested slot composition. citeturn13view0turn13view1

**Asset extraction** — это выгрузка изображений, SVG, PNG, PDF и бинарных изображений из файла. В Figma это опирается на file/image endpoints, plugin image APIs и export settings. С инженерной точки зрения главный вывод здесь простой: asset pipeline нельзя оставлять на LLM inference. Figma already knows hashes, bytes, export formats и node-scoped image representations; значит, в Pixel Factory asset retrieval должен быть deterministic. LLM может решать, куда asset вставить, но не должна “домысливать” сам asset. citeturn13view2turn13view3turn11view17

В research-плоскости главный урок еще жестче. Design2Code показывает, что современные модели в среднем отстают именно в **recalling visual elements** и в **correct layout designs**. WebSight строит большой synthetic dataset именно потому, что screenshot-to-HTML без сильного supervised grounding плохо масштабируется. UI2Code^N и LayoutCoder движутся дальше: они формализуют extraction/generation как feedback-driven loop, а не как single-pass translation. Для WF-A03 это означает, что extraction layer должен быть самостоятельным модулем, а не побочным эффектом генерации. citeturn12view0turn12view4turn12view5turn12view6

## Pixel QA And Validation Systems

Рынок visual QA фактически стандартизировался вокруг baseline comparison. **Playwright** — это локальный или CI-first способ делать screenshot assertions; он генерирует reference-screenshots и сравнивает последующие рендеры с baseline. При этом он умеет ждать стабилизации двух последовательных скриншотов, отключать анимации, скрывать caret, маскировать динамические элементы, задавать `threshold`, `maxDiffPixels` и `maxDiffPixelRatio`. То есть даже на уровне простого open-source инструмента индустрия уже пришла к одной мысли: без стабилизации состояния и аккуратного diff не бывает надежного pixel QA. citeturn11view7turn13view11turn14view0turn14view1turn14view2

**BackstopJS** — классический open-source visual regression runner. Его модель проста и именно поэтому до сих пор жива: задать URL, screen sizes, selectors, interactions; снять test screenshots; сравнить их с reference screenshots; выдать visual report. Это хороший эталон для page-level regression, когда нужен прозрачный screenshot pipeline без тяжелой SaaS-инфраструктуры. Для Pixel Factory BackstopJS важен как пример легкого page-diff контура, который можно встраивать в batch validation поверх generated frontend. citeturn11view8turn5search9

**Percy** добавляет важный architectural shift: он не просто сравнивает готовые изображения, а **захватывает DOM и assets в тестовом браузере, а затем рендерит snapshots на своей инфраструктуре в разных браузерах и widths**. Это переводит нас от простого image diff к более сильному render validation. Percy также формализует review/approve workflow, responsive widths и deferred uploads для объединения responsive snapshots с одинаковым именем. Именно такой тип системы особенно полезен для responsive drift и cross-browser drift, потому что baseline привязан уже не только к определенному локальному runtime. citeturn11view9turn11view18turn13view8turn13view9

**Chromatic** специализируется на component-level visual testing поверх Storybook. Его ключевой вклад — не столько “снимок как картинка”, сколько **изолированная baseline-проверка компонентов** и встроенный review flow в CI. Дополнительно TurboSnap использует git history и dependency graph, чтобы прогонять только изменившиеся stories и копировать baselines для неизменившихся. Это лучший образец component QA practice: сначала isolate component surface, потом snapshot, потом review, и только затем merge. Для Pixel Factory это особенно важно, если система будет опираться на component mapping и library-first кодогенерацию. citeturn11view10turn11view19turn13view10

Если разложить **validation systems** по технике, то картина такая. **Screenshot pipeline** — это воспроизведение состояния, стабилизация, capture baseline, capture candidate. **Image diff** — pixel-level сравнение, часто с perceptual thresholds; хороший пример — pixelmatch, который ориентирован именно на screenshot comparison и поддерживает anti-alias-aware/perceptual difference logic. **Render diff** — это уже capture DOM/assets + повторный рендер в стандартизированной инфраструктуре, что особенно характерно для Percy. **Layout diff** в mainstream production чаще всего не существует как отдельный продуктовый слой; обычно он реализуется как комбинация component isolation, full-page screenshots на нескольких breakpoints и diff-порогов, плюс human review там, где автоматике трудно понять критичность сдвига. citeturn8search0turn11view18turn13view8turn11view10turn11view19

Вывод по Part 3 и Part 4 жесткий: **pixel-perfect production без visual baselines — это не production**, а демонстрация. Современный рынок подтверждает, что даже сильные генераторы должны после себя проходить через screenshot/render validation контур. И именно этот контур сегодня является реальным качественным барьером между “AI сгенерировал интерфейс” и “интерфейс готов к релизу”. citeturn11view7turn11view9turn11view10turn12view5

## Production Pipelines

С точки зрения мировой практики наиболее типовой pipeline действительно выглядит близко к вашей формуле:

> **Vision / Design Input**  
> → **Extract / Normalize**  
> → **Map To Components / Design System**  
> → **Generate Code**  
> → **Render**  
> → **Diff**  
> → **Fix / Refine**  
> → **Approve**  
> → **Merge / Deploy**  

Именно к такой схеме нас подводят и коммерческие системы, и research. Builder делает component mapping и codebase integration. Locofy сначала заставляет оформить semantic meaning и custom component mapping. v0 и Lovable добавляют repo-aware generation и repair. UI2Code^N прямо формализует closed-loop execution, visual inspection и iterative refinement. Percy и Chromatic фиксируют финальный approval gate. citeturn11view1turn16search1turn19view3turn19view4turn12view5turn11view9turn11view10

На практике существует две рабочие ветки. **FIGMA→HTML ветка** начинается с node tree, components, instances, assets и design system metadata. Здесь extraction максимально deterministic, а генерация должна быть ограничена правилами кодовой базы. **PNG→HTML ветка** стартует со screenshot/sketch, поэтому должна сначала построить layout tree и element hypotheses; именно здесь наиболее полезны WebSight/Design2Code-подходы и iterative visual optimization. Waveform для Pixel Factory отсюда очевиден: Figma branch должна быть приоритетной и более автоматизированной, PNG branch — вторичной и более проверяемой. citeturn13view3turn13view0turn13view2turn12view4turn12view0turn12view5turn12view6

Также видно, что зрелые системы почти всегда добавляют **repo synchronization**. Builder CLI встраивает код в существующий codebase; v0 генерирует в реальной repo/sandbox environment; Lovable и Git integration держат two-way sync, branches и PR creation. Это важный организационный вывод: production pipeline заканчивается не на “скачай zip”, а на “результат живет в versioned engineering workflow”. Для WF-A03 это должно быть обязательной частью архитектуры. citeturn11view1turn19view3turn19view7

## Failure Classes

Типовые failure classes, которые повторяются и в research, и в коммерческих workflow, хорошо совпадают с вашим списком. **Asset mismatch** возникает, когда pipeline теряет правильный asset source, crop, size, format или hash. Это особенно типично, когда asset extraction недетерминированный или когда генератор пытается “воспроизвести” изображение вместо извлечения оригинала. Детерминированный Figma asset pipeline эту проблему сильно уменьшает, потому что API уже дает image bytes, hashes и export formats. citeturn13view2turn13view3turn11view17

**Component mismatch** — один из самых дорогих классов ошибок. Он появляется, когда визуально похожий блок не связывается с правильным code component, variant или prop model. Builder и Locofy обеими руками показывают, что без явного component mapping и prop mapping здесь нельзя полагаться на one-shot inference. В production это обычно проявляется как “похоже на кнопку, но не тот variant/state/slot/behavior”. citeturn11view0turn19view1turn16search1turn16search6

**Text hallucination** и **omission drift** — отдельная боль screenshot-to-code. Design2Code прямо описывает cases, где self-revision добавляет missing texts или исправляет layout errors, а исследование в целом показывает слабость моделей в visual element recall. Иными словами, модель может упустить текст, перефразировать его или подставить правдоподобный, но неверный content. Это особенно критично в hero, pricing, legal, CTA и data-heavy блоках. citeturn10search1turn12view0

**Ordering drift** обычно рождается на границе layout parsing и code generation: визуальный порядок распознан примерно верно, но DOM order, flex direction, tab order или stacking context оказываются другими. UI2Code^N отдельно подчеркивает, что spacing, alignment и typography tight-coupled, а runtime feedback нужен именно потому, что единичный кодовый прогноз brittle. Ordering drift часто выглядит как “почти тот же экран”, но ломает accessibility, wrappers или responsive collapse behavior. citeturn12view5

**Layout drift** — самый ожидаемый и самый частый класс ошибок. Design2Code выводит его напрямую: модели отстают в correct layout designs. LayoutCoder строится ровно на признании того, что MLLM-based UI2Code трудно понимать complex layouts и сохранять layout faithfully. Если переводить это в инженерный язык, то основные риски — spacing, alignment, size relations, nested containers, grids, overlays и absolute positioning. citeturn12view0turn12view6

**Responsive drift** появляется тогда, когда desktop выглядит приемлемо, а на breakpoints система теряет intended behavior. Percy решает это через widths/responsive snapshots; Anima и Locofy прямо опираются на breakpoints, auto-layout и responsive configuration; Playwright и BackstopJS решают проблему через multiple viewport baselines. Это означает, что responsive correctness — не дополнительная опция, а обязательный класс validation. Один screenshot на desktop не доказывает ничего о production fidelity. citeturn13view8turn4search1turn13view7turn16search15turn11view8turn11view7

Отдельно стоит выделить **render drift**, хотя вы не вынесли его в failure list. UI2Code^N объясняет, почему он возникает: browser defaults, font fallback и DPI scaling дают реальное расхождение между кодом и целевым видом. Отсюда ключевой вывод для Pixel Factory: даже идеально сгенерированный JSX/CSS нельзя считать финальным, пока он не прошел реальный рендер и diff против эталона. citeturn12view5

## Human-In-The-Loop Models

Современные системы не убирают человека из контура; они **смещают человека в точки максимальной ценности**. Первая такая точка — **component/design-system grounding**. Builder позволяет remap components, если AI ошибся. Locofy требует designer/plugin-side mapping и validation для custom components и prop mapping. Stitch развивает DESIGN.md как переносимый design-rules layer, а не как скрытую магию модели. Это означает, что человек нужен там, где нужно определить semantic identity интерфейса. citeturn11view0turn16search1turn16search6turn20view4

Вторая обязательная точка — **visual review и approval**. Percy прямо строит reviewer workflow с review/request changes/approve. Chromatic синхронизирует baselines между ветками и участниками, а PR checks становятся частью merge gate. Даже при хорошем diff engine финальное решение о значимости изменения все равно принимает человек, потому что машинный diff видит “изменилось”, но не всегда понимает, “плохо это или ожидаемо”. citeturn11view9turn11view10turn11view19

Третья точка — **spatial correction и ambiguity resolution**. Lovable особенно хорошо показывает этот паттерн: пользователь выбирает элемент в preview, рисует annotation, прикладывает image update, затем описывает изменение короткой инструкцией. Это хороший образец того, как human-in-the-loop должен работать в Pixel Factory: человек не переписывает верстку руками, а дает точное пространственное указание системе. citeturn19view5turn19view6

Четвертая точка — **debugging unexpected behavior**. Любая зрелая production system должна признавать, что ошибки бывают не только compile/runtime, но и semantic/visual. Lovable для этого предлагает Try to Fix по логам и fallback в revert/re-prompt; v0 делает ставку на autofixers; UI2Code^N вообще строит refinement вокруг rendered feedback. То есть зрелый human-in-the-loop — это уже не “человек делает все руками”, а “человек вмешивается после детерминированного сигнала о проблеме”. citeturn19view8turn19view4turn12view5

## Foundry Gap Analysis And Recommendations For WF-A03

По вашему брифу FOUNDRY уже имеет **WF-A01 COMPLETE**, **WF-A02 COMPLETE**, **WF-R01 ACTIVE**, а **WF-A03 Pixel Factory** — deferred. При этом содержимое **VL3** и **FP-0002 findings** в доступных мне источниках этой сессии не нашлось, поэтому сопоставление по ним будет ограниченным и должно считаться предварительным.

Если опираться на мировую практику, самый вероятный разрыв в текущем состоянии FOUNDRY — это не отсутствие еще одного генератора, а отсутствие **центрального production orchestrator-а**, который бы связывал extraction, mapping, generation, render validation и approval в единый контур. Именно этот слой и выглядит как логичная роль для WF-A03, потому что рынок уже доказал: value возникает не в Figma-to-code как таковом, а в **control loop** вокруг него. citeturn11view1turn12view5turn11view18turn11view19

В терминах gap analysis мировой best practice требует от Pixel Factory как минимум семи обязательных capability blocks. Нужен **structured ingest** для Figma и image ingest для PNG/screenshots. Нужен **normalized intermediate representation**, где отдельно живут layout tree, components, instances и assets. Нужен **design-system/component mapping layer**. Нужен **generator layer** с repo grounding. Нужен **render lab** для local/cloud rendering на нескольких widths. Нужен **diff engine** с baseline management. И нужен **approval gate** поверх reviewer workflow. Если WF-A01/A02 уже покрывают часть foundation/analysis, а WF-R01 держит активный runtime/validation слой, то именно WF-A03 должен соединить их в market-grade pipeline. citeturn13view3turn13view0turn13view2turn11view1turn11view18turn11view9turn11view10

Рекомендация для **WF-A03** однозначная. Делать его нужно не как “универсальный AI-верстальщик”, а как **Foundry Pixel Factory orchestration layer** с двумя режимами. Первый режим — **Figma-native deterministic lane**: node extraction, component/instance/assets, code generation с component mapping, render/diff/approve. Второй режим — **vision lane** для PNG/sketch/external reference: layout parsing, draft generation, multi-pass render/diff/fix. В обоих режимах human review должен сидеть не в середине всей работы, а в трех узких местах: mapping, exception handling, final approval. citeturn19view1turn16search1turn12view5turn12view6turn11view9turn11view10

Если формулировать еще жестче, то **WF-A03 не стоит откладывать как nice-to-have**. Именно он закрывает разницу между “есть отдельные AI и render-наработки” и “есть производственный AI-driven frontend pipeline”. Без него Foundry рискует остаться на уровне набора разрозненных capability blocks. С ним можно собрать систему, соответствующую тому, как рынок реально решает PNG→HTML, FIGMA→HTML, design→code, pixel-perfect production и visual QA в 2025–2026 годах. citeturn12view5turn19view4turn11view18turn11view19
