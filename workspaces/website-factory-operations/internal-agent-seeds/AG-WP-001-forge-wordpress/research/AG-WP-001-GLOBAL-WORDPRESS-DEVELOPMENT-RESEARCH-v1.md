## Что считается зрелой практикой AI-assisted разработки

Главный сдвиг 2024–2026 годов — переход от «чат-генерации кода» к **агентам с инструментами, проектными инструкциями, планированием, запуском тестов и review-loop**. GitHub Copilot cloud agent умеет исследовать репозиторий, строить implementation plan, менять код на отдельной ветке и формировать pull request; GitHub Copilot CLI и Agent Mode работают с approval prompts, trusted folders, custom instructions и автоматическим code review. Cursor развивает Rules, Plan Mode, sandboxed terminal, isolated Git worktrees и subagents. Claude Code отдельно фиксирует model permissions, sandboxing и layered enforcement для Bash, Read, Edit, WebFetch и MCP. citeturn30search6turn30search3turn30search7turn24search2turn24search9turn30search0turn30search8turn29search0turn29search5turn29search2turn29search11turn24search0

То есть современная зрелая практика — это не «один большой промпт», а минимум четыре обязательных слоя управления. Во-первых, **persistent project instructions**: `.github/copilot-instructions.md`, path-specific instructions, `AGENTS.md`, Cursor Rules и аналогичные файлы, которые описывают как проект устроен, где лежит код, как его билдить, тестировать и валидировать. Эта инженерная дисциплина подтверждается и исследовательскими источниками. SWE-bench и особенно SWE-bench Verified показывают, что реальная software engineering оценка должна строиться на проверяемых issue-level задачах, а не на игрушечных генерациях. ## Как выглядит современная WordPress-реализация production-уровня

В современной профессиональной WordPress-практике почти везде повторяется одна и та же организационная идея: **presentation и business/content logic должны быть разведены**. WordPress Plugin Handbook прямо рекомендует размещать custom post types в плагине, а не в теме, чтобы контент оставался переносимым при смене темы. Это же подтверждает практика 10up: их `wp-scaffold` создаёт bare bones theme и must-use plugin как базу проекта, а их block theme training project хранит CPT и taxonomies в плагине, а тему — отдельно. На WordPress VIP дополнительно фиксируется, что плагины, темы и custom code ведутся только через version-controlled repository, а не через ad-hoc изменения в WP Admin. citeturn4search4turn8search1turn8search4turn8search12turn7search0turn7search13

С точки зрения theme architecture рынок 2024–2026 годов уже нельзя описывать только словами «classic theme или block theme». Реально используются три рабочих модели. **Block theme** естественно подходит там, где утверждённую frontend-вёрстку можно выразить через templates, template parts, patterns и `theme.json`; WordPress Theme Handbook прямо описывает block theme как тему, построенную в основном на HTML и theme configuration file, а Create Block Theme и Playground дают workflow для переноса изменений из Site Editor обратно в файловую систему и GitHub. **Classic или hybrid theme** остаётся оправданным там, где нужно очень точное управление PHP-шаблонами, произвольной HTML-структурой и legacy/editor surface. И наконец, **theme + functionality plugin** остаётся самой повторяемой production-моделью для bespoke-проектов. citeturn2search8turn2search9turn2search2turn2search5turn16search0turn17search0

Для динамического слоя WordPress с 6.5 по 7.0 сильно усилил блоковый стек. `block.json` официально рекомендован как canonical-способ регистрации блоков на сервере и клиенте; server-side registration считается best practice, потому что включает dynamic rendering, block supports и другие возможности. Block Bindings API в 6.5+ позволяет подцеплять динамические данные к атрибутам core blocks без написания отдельных custom blocks для каждого случая. Interactivity API, публично представленный в 6.5 и дорабатывавшийся в 6.6 и 6.9, стал стандартным способом добавлять фронтенд-интерактивность в блоки и шаблоны. Для систем уровня WP Forge это означает, что конвертация в WordPress уже не обязана сводиться к голым PHP-template files: всё чаще production-quality решение — это комбинация templates, server-registered blocks, bindings и официальных frontend APIs. citeturn26search0turn26search2turn26search4turn26search7turn1search14turn1search18turn0search0turn11search14

Практически во всех современных bespoke-воркфлоу ACF остаётся главным прагматичным слоем для content modeling. ACF даёт field groups, options pages, CPT/taxonomy registration через UI, Local JSON для version control и синхронизации между окружениями, а с 6.8 добавил WP-CLI-команды для JSON import/export/sync и интеграцию с Abilities API для AI-discoverable field groups, CPT и taxonomies. Одновременно ACF Blocks остаются очень важным мостом между PHP-first разработкой и block editor: ACF рекомендует `block.json`-регистрацию блоков, а сами ACF Blocks позволяют создавать кастомные блоки без обязательной React-разработки. Для команды, которая берёт уже готовую HTML/SCSS/JS-вёрстку и должна быстро собирать управляемый редакторский surface, это сегодня один из самых практичных и массово используемых путей. citeturn0search1turn0search7turn4search3turn33search3turn33search5turn33search10turn5search0turn5search1turn18search2turn18search7turn18search15

Отдельно видно, что современный WordPress всё активнее двигается к **управляемому admin UX**, а не к идее «пускай редактору доступно всё». Data Views и DataForm с 2024 по 2026 превратились в реальный toolkit для data-heavy plugin/admin screens. Параллельно content-only editing, block locking и pattern editing позволяют защищать дизайн и структуру, оставляя редактору только те поля и участки, которые ему действительно нужно менять. Это соответствует общей мировой практике AI-assisted систем: сначала проектируется **разрешённая поверхность изменений**, и только потом на неё допускаются автоматизация и агенты. citeturn22search0turn22search1turn22search2turn22search10turn31search2turn31search5turn27search0turn27search2turn27search16turn27search14

## Исследовательский паттерн преобразования вёрстки в WordPress implementation

Высококонфидентный вывод по мировой практике такой: качественная система «frontend-to-WordPress» почти всегда работает как **многоэтапный supervised pipeline**, а не как один шаг генерации. На первом этапе она извлекает из утверждённой вёрстки структуру: типы экранов, повторяющиеся секции, различие между layout и content, интерактивные сценарии, повторяемые карточки, архивы, single-views, forms, глобальные design tokens и области, которые потенциально станут editable. Это хорошо сочетается с современными planning modes и project rules у coding agents, где сначала строится reviewable plan, и только потом начинается изменение кода. citeturn29search5turn30search0turn30search4turn24search14

На втором этапе зрелые системы не пытаются автоматически «загнать всё в один стиль реализации». Они делают **item-by-item выбор surface**: что станет theme template, что pattern, что template part, что custom block, что ACF Block, что обычный PHP template, а что должно остаться полностью неeditable. Это прямо согласуется с текущей WordPress-архитектурой, где block themes, template parts, `theme.json`, `block.json`, Block Bindings и Interactivity API дают разные уровни выразительности, а content-only editing и block locking — разные уровни защиты структуры. Для WP Forge это, по сути, главный методологический вывод: хорошая система должна сначала принимать решение о правильной форме WordPress-представления каждого участка frontend-а, а не шаблонно конвертировать весь сайт одним и тем же способом. citeturn2search2turn2search5turn26search0turn26search7turn26search19turn27search0turn27search16

На третьем этапе формируется **content model как отдельный артефакт**, а не как побочный эффект шаблонов. Зрелая практика требует отдельно определить post types, taxonomies, meta, REST exposure, capabilities, relationship fields, options pages и editorial rules. В native WordPress это выражается через `register_post_type`, `register_taxonomy`, `register_meta` и `show_in_rest`; в ACF — через field groups, CPT/taxonomy UI, Local JSON и JSON/CLI sync. Именно здесь человеческий review особенно нужен, потому что ошибка в content model дороже, чем ошибка в template markup: неправильно названный CPT, плохо выбранная taxonomy hierarchy или неудачная редакторская модель потом ломают весь проектный UX. citeturn4search0turn4search1turn4search2turn4search4turn4search6turn33search3turn33search5turn33search10

На четвёртом этапе implementation должен происходить **не в production и не в живой админке**, а в воспроизводимом dev/staging runtime. Здесь WordPress за последние два года резко усилился: Playground даёт браузерный WordPress, Blueprints дают declarative setup, `wp-env` получил Playground runtime без Docker, а Playground CLI рекомендован вместо `wp-now`. В 2026 году WordPress добавил и официальный Playground MCP server, чтобы coding agents могли читать/писать файлы, исполнять PHP, управлять сайтом и ходить по страницам локально, без опасной привязки к production admin. Это очень близко к тому, каким должен быть runtime для WP Forge: **одноразовый, быстро поднимаемый, тестируемый и уничтожаемый**. citeturn2search0turn10search4turn10search3turn10search7turn32search1turn32search2turn32search6turn32search7

На пятом этапе implementation проходит полный quality loop: статический анализ, unit/integration tests, E2E, visual checks и review preview. Здесь особенно показательно, что WordPress в 2025–2026 не просто «терпит» такой процесс, а активно его поддерживает: WP-CLI умеет scaffolding для plugin/theme tests; Playwright уже введён в официальные WordPress materials как путь для E2E; в WordPress 6.9 появился `assertEqualHTML()` для семантического сравнения HTML; Playground PR Preview action позволяет открывать theme/plugin PR как готовый WordPress preview в браузере. В мировом engineering-смысле это тот самый признак зрелости платформы: автоматизация не заменяет инженера, а создаёт для него более дешёвую и быструю проверку результата. citeturn19search0turn19search3turn19search5turn15search1turn9search2turn28search0turn32search7

## Безопасность и human supervision как обязательный слой

Для WP Forge принципиально важно не путать два разных класса AI-интеграции. Первый класс — **assistive development agent**: он работает с кодом, тестами, sandbox-сайтом, pull request и внутренними спецификациями. Второй класс — **runtime agent inside live WordPress**: он получает доступ к реальным данным и управлению сайтом. Современная best practice допускает первый класс как уже зрелый, а второй — только в сильно ограниченных сценариях. Именно поэтому GitHub, Cursor и Claude так много внимания уделяют trusted directories, permission prompts, sandboxing, custom instructions и review loops. citeturn24search2turn24search6turn24search9turn29search0turn29search2turn29search11turn30search15

WordPress-специфическая часть той же логики выражена через security- и permission-модель платформы. Official handbooks требуют sanitizing, validating и escaping данных, использование nonces, проверок capabilities и корректной защиты admin / REST actions. Если агент генерирует WordPress-код, он должен автоматически подчиняться именно этим invariants, иначе он будет быстро производить production-looking, но небезопасный код. Иными словами, качество WP-агента определяется не красотой PHP-шаблона, а тем, насколько стабильно он соблюдает `current_user_can`, nonces, sanitization/validation/escaping и корректную модель meta/REST exposure. citeturn3search0turn3search1turn3search2turn3search3turn3search8turn3search10turn3search15turn3search18

Очень важный тренд 2025–2026 — появление **typed, discoverable, permission-aware WordPress interfaces for agents**. Abilities API вводит явные inputs/outputs/permissions для capabilities; MCP Adapter переводит их в MCP tools/resources; ACF 6.8 поверх этого начал публиковать field groups/CPT/taxonomies как AI-discoverable abilities; AI Client и Connectors API в 7.0 стандартизируют доступ к внешним AI providers. Это большой шаг вперёд по сравнению с «агент кликает в админке», потому что машинное взаимодействие начинает идти через явные схемы и permission callbacks. Но именно поэтому production-политика должна быть строгой: если WP Forge когда-либо будет использовать такие интерфейсы, разумная мировая практика — сначала раскрывать агенту только sandbox/dev/staging abilities и только потом думать о более широком surface. Это уже не факт из одной конкретной документации, а прямой исследовательский вывод из совокупности источников. citeturn13search0turn13search2turn13search5turn14search2turn14search1turn5search0turn5search2turn21search1turn21search10

Enterprise WordPress-платформы фактически подтверждают ту же идею. На WP VIP код, плагины и темы не ставятся через FTP или свободный dashboard workflow; они держатся в version-controlled repository, кодоактивируются, проходят PR analysis, linting и vulnerability/update scan, а на платформе уже есть инструменты вроде VIP Code Analysis Bot и Codebase Manager. Это практически эталонный образец того, как должен выглядеть human-supervised контур вокруг WP Forge: агент может ускорять разработку, но не должен самовольно становиться production control plane. citeturn7search0turn7search1turn7search2turn7search7turn23search2turn23search6turn23search10

## QA, visual regression и quality gates

Если смотреть на зрелые инженерные цепочки, то minimum quality bar для AI-generated WordPress implementation сегодня уже довольно понятен. Во-первых, нужен **статический и стайл-анализ**. Официальный WordPress Coding Standards проект для PHPCS — де-факто базовый стандарт. 10up прямо завязывает свои best practices на WordPress coding standards и PHPCS, а на VIP те же проверки встроены в Code Analysis Bot. Для системы типа WP Forge это означает, что любой autogenerated PHP должен считаться незавершённым до прохождения WPCS/PHPCS и проектных rulesets. citeturn9search0turn9search3turn9search9turn8search0turn7search2turn7search6

Во-вторых, нужен **PHP/unit/integration слой**, а не только browser smoke test. WP-CLI умеет scaffold для plugin tests и theme tests; его plugin scaffold уже создаёт `phpunit.xml.dist`, bootstrap, sample tests и `.phpcs.xml.dist`. WordPress 6.9 добавил `assertEqualHTML()` в `WP_UnitTestCase`, что особенно полезно именно для задач WP Forge: generated render callbacks, filters, HTML API transformations и block markup теперь можно сравнивать семантически, а не как хрупкие строковые литералы. citeturn19search0turn19search3turn19search5turn28search0turn28search2

В-третьих, нужен **editor/front-end E2E слой**. В 2026 WordPress Developer Blog уже официально продвигает Playwright как практический способ писать E2E tests для block variations, patterns и front-end behavior. Playwright же официально поддерживает visual comparisons через `toHaveScreenshot()`. Для WordPress-проектов это особенно важно, потому что correctness часто лежит не в голой логике, а в сочетании templates, blocks, CSS, editor state и фронтенд-вывода. Visual regression здесь не «nice to have», а один из редких способов массово обнаруживать проблемы конвертации frontend в theme implementation. citeturn15search1turn9search2turn9search8

В-четвёртых, нужен **preview/review surface для человека**. WordPress Playground PR Preview Action позволяет привязать к pull request кнопку мгновенного запуска браузерного WordPress preview для plugin/theme изменений. Одновременно Playground, Blueprints и CLI сокращают цену воспроизводимого тестового окружения почти до нуля. Это означает, что современная мировая практика уже технически позволяет сделать для WP Forge очень сильный review loop: агент создал implementation, CI поднял preview, человек сравнил со frontend-эталоном, после чего либо утвердил, либо вернул на доработку. citeturn32search7turn10search0turn10search4turn10search3

Наконец, нужен **plugin governance и security QA**, потому что WordPress implementation почти всегда включает сторонние расширения. Тут рынок чётко показывает зрелый паттерн: до активации плагины исследуются, сканируются и тестируются в non-production environment. WP VIP прямо требует именно этого, а WPScan / Patchstack / VIP Codebase Manager уже используют vulnerability databases и update scans для plugin/theme risk management. Для WP Forge это особенно критично, потому что agentic система по своей природе склонна «ускорять интеграцию», а значит — ускорять и перенос уязвимых зависимостей, если заранее не встроить security gate. citeturn7search7turn23search2turn23search4turn23search5turn23search10

## Что из этого напрямую важно для WP Forge

Самая надёжная часть исследования сводится к трём практическим выводам.

Первый вывод: **наиболее зрелая зона автоматизации — implementation under supervision, а не autonomous site control**. Уже сегодня достаточно зрелы: анализ утверждённой вёрстки, построение implementation plan, генерация theme/plugin skeletons, проектирование content model, генерация ACF/CPT/taxonomies, сборка templates и custom blocks, подготовка admin panels, scaffolding тестов, запуск Playwright/PHPUnit/PHPCS, поднятие preview и формирование PR-артефактов. Всё это хорошо согласуется и с общими coding-agent практиками, и с тем, как WordPress развил Playground, `wp-env`, block APIs, DataForm/DataViews и preview tooling. citeturn29search5turn30search15turn10search4turn16search0turn19search3turn15search1turn32search7turn22search1

Второй вывод: **WordPress implementation уровня production почти наверняка должен собираться как комбинация theme artifacts и functionality artifacts**, а не как одна большая тема. Это подтверждают WordPress Plugin Handbook, 10up scaffold/training и VIP-процессы. Следовательно, если система берёт готовый frontend и делает из него WordPress, ей нужен отдельный этап принятия решения: что принадлежит теме, что must-use/plugin слою, что content-model слою, а что editor-governance слою. Без этого любая AI-автоматизация будет быстро производить удобный, но плохо сопровождаемый монолит. citeturn4search4turn8search1turn8search12turn7search0

Третий вывод: **наиболее перспективные WP-native AI building blocks уже появились, но использовать их надо осторожно**. Abilities API, MCP Adapter, Playground MCP, AI Client, Connectors API и ACF 6.8 AI-discoverable surface реально открывают путь к WordPress-aware агентам нового класса. Но на июнь 2026 это скорее фундамент для controlled toolchains, чем доказательство того, что production WordPress можно безопасно отдать автономному агенту. Для WP Forge это хорошая новость: можно строить систему уже сейчас, используя эти примитивы как ускорители в sandbox/dev/staging контуре, не нарушая границу «WP Forge не является автономным runtime и не должен самостоятельно управлять production». citeturn13search0turn14search2turn21search1turn21search10turn32search1turn5search0

С точки зрения high-confidence research findings, зрелыми для WP Forge выглядят такие принципы:

- **Spec-first и plan-first вместо prompt-first.** Современные coding agents дают лучший результат, когда у них есть постоянные project instructions, reviewable plan и test/validation commands, а не только свободная формулировка задачи. citeturn30search0turn30search4turn29search5turn24search14
- **Sandbox-first environment.** WordPress Playground, Playground CLI, `wp-env` runtime=playground и PR previews уже дают достаточно сильную базу для одноразовых безопасных WordPress-окружений, в которых агент может работать без доступа к production. citeturn10search4turn10search3turn32search2turn32search7
- **Version-controlled content model.** ACF Local JSON, ACF JSON CLI, plugin-based CPT/taxonomy surfaces и Git-managed codebase — это текущая зрелая норма, а не опция. citeturn33search3turn33search5turn33search10turn4search4turn7search0
- **Curated editor, not open editor.** DataForm, DataViews, content-only editing, block locking и pattern control показывают направление рынка: профессиональные системы проектируют не просто вывод сайта, а границы редакторского вмешательства. citeturn22search0turn22search1turn27search0turn27search16turn27search14
- **PR-gated QA as the true acceptance surface.** WPCS/PHPCS, PHPUnit, `assertEqualHTML()`, Playwright, screenshot diffs, vulnerability scans и browser preview — это минимальный каркас доверия к AI-generated implementation. citeturn9search0turn28search0turn15search1turn9search2turn23search10turn32search7

## Открытые вопросы и ограничения

Это исследование даёт достаточно твёрдую основу для проектных решений уровня policy, workflow и boundaries, но оставляет несколько осознанно открытых вопросов, которые должны решаться уже на следующем этапе, а не внутри этого отчёта.

Во-первых, остаётся проектный выбор **какая доля сайтов WP Forge должна целиться в block theme workflow**, а какая — в hybrid/classic. Источники показывают, что block stack стал намного сильнее, но не доказывают, что он оптимален для каждого bespoke frontend-а без исключений. citeturn2search8turn16search0turn17search0turn26search0

Во-вторых, остаётся открытым, **делать ли ACF обязательным системным слоем или поддерживать его как один из режимов**. С одной стороны, ACF сегодня очень силён и всё глубже интегрируется в machine-readable WordPress. С другой, core WordPress тоже быстро развивается в сторону typed fields, DataForm/DataViews, Abilities и новых content-type primitives. citeturn5search0turn33search10turn31search2turn31search5turn21search7

В-третьих, дальнейшее проектирование неизбежно должно формализовать **handoff contract между WP Forge и WPilot**: какие зоны implementation замораживаются, какие могут меняться позже, как фиксируются editable regions, и какой уровень automations допустим после передачи. Публичные источники хорошо описывают инструменты и практики, но этот конкретный operational contract остаётся внутренней проектной задачей.
