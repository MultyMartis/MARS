# Triumph Manipulator Landing V3 — Execution Plan

## Purpose

This plan prepares the V3 workspace for first real Forge execution. It defines reconstruction strategy and readiness boundaries only.

This initialization does not rebuild sections, tune visuals, claim fidelity, or claim production readiness.

## Governance Mode

Default mode: adaptive standard.

Use lightweight governance only for clear, local, reversible setup work. Escalate to critical mode when source authority, responsive intent, strategic hierarchy, implementation survivability, QA confidence, or V2 contamination risk becomes material.

## Reconstruction Order

1. Confirm V1 source pack boundary.
2. Build from `design/v1/01.png` through `design/v1/04.png` in natural vertical order.
3. Use `design/v1/full.png` only as continuity reference until its authority relationship is confirmed.
4. Inspect `design/shared-assets/` before declaring logo, hero/media, vehicle/manipulator, social/icon, review, or other visual assets `UNKNOWN`.
5. Establish section names only after source analysis identifies stable semantic roles.
6. Implement one source slice or section scope at a time.
7. Run focused build and QA checks after each meaningful source-to-build transfer.
8. Record approximations, unknowns, and escalation decisions before continuing.

## Section Sequencing

Initial sequencing follows the V1 strip order:

- `01.png`: first landing slice; likely high-priority hierarchy and conversion zone, but semantic naming remains unconfirmed.
- `02.png`: second landing slice; implementation scope not yet named.
- `03.png`: third landing slice; implementation scope not yet named.
- `04.png`: final landing slice with different export dimensions; must receive extra layout and continuity review.

Do not import V2 section names or V2 homepage order into this sequence.

## Asset Authority

`projects/triumph-manipulator-landing/design/v1/` is the layout/design authority for V3.

`projects/triumph-manipulator-landing/design/shared-assets/` is the approved asset authority for V3. It may supply logos, social icons, review marks, and any future approved media assets that are present in that folder.

Shared assets must support the V1 reconstruction. They must not override V1 section structure, hierarchy, composition, visual intent, or screen order.

The previous Screen 01 pass made an incomplete missing-asset claim because `design/shared-assets/` was not treated as approved authority. Future source analysis must inspect and map shared assets before recording asset gaps.

## Responsive Strategy

Responsive behavior must be reconstructed conservatively because current V1 authority is raster-based and desktop-oriented.

Initial approach:

- Preserve source hierarchy before visual compression.
- Keep semantic grouping readable under collapse.
- Use mobile layout decisions only when they can be justified from source intent or explicitly disclosed as approximation.
- Treat unresolved mobile composition as SAFE UNKNOWN rather than inventing confidence.
- Add breakpoints only when they protect source intent or maintainability.

## Approximation Disclosure Policy

Every approximation must be visible in the relevant work report or future section note.

Disclose:

- What was approximated.
- Which source was insufficient.
- Why the approximation is conservative.
- Whether HITL is recommended or required.
- What evidence would replace the approximation.

Hidden approximation is a failure condition.

## Escalation Conditions

Pause and escalate when:

- V1 source authority is missing, contradictory, unreadable, or insufficient.
- `design/shared-assets/` lacks a required implementation asset after inspection.
- V2 offers an answer that V1 does not.
- A decision changes copy, CTA priority, visual hierarchy, trust/proof order, or section meaning.
- Mobile collapse would materially alter source intent.
- Implementation would require a brittle local patch or unclear ownership.
- QA evidence is too weak for the confidence being claimed.

## QA Checkpoints

Use proportional QA:

- Build check after starter readiness and after each future section scope.
- Source lineage check before each implemented slice/section.
- Visual intent check against the active V1 source export.
- Responsive survivability check for each implemented scope.
- Accessibility sanity check for landmarks, headings, links/buttons, and focusable controls.
- Maintainability check for file ownership, naming, and future edit safety.

PASS language must stay scoped to evidence. Build success alone does not prove fidelity or production readiness.

## Reporting Expectations

Reports should be concise and evidence-based:

- Changed files.
- Source basis.
- What was implemented or prepared.
- What was not implemented.
- SAFE UNKNOWN.
- Approximation disclosure.
- QA evidence.
- V2 contamination protection.
- Remaining blockers.

## Current Initialization Boundary

This phase creates only the V3 workspace, documentation lock, source-first scaffold, and build readiness baseline.

It explicitly does not rebuild hero, sections, final visuals, responsive behavior, or production packaging.
