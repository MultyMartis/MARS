# CALLBACK LOOKUP REPAIR v1 — Phase 3F.2

## Fix 1 — single canonical token algorithm (IMPLEMENTED, code-level)

`computeActionToken()` in `implementation/runtime-libs/formatter-lib.mjs` no longer attempts Node `crypto`/SHA-256 at all — it always calls the dual-hash `fnvToken()` directly:

```js
/**
 * Canonical opaque lead callback token (Phase 3F.2).
 * Always dual-FNV fnvToken — never Node crypto — so harness and n8n match.
 */
export function computeActionToken(leadId) {
  return fnvToken(String(leadId || ''));
}
```

This removes the `try/catch` branch that silently masked the real algorithm being used in production (n8n disallows `crypto`, so the fallback was always taken anyway — the fix makes that explicit instead of implicit).

Admin Handle Callback's verifier was aligned to call the **same** canonical `fnvToken` — the simplified single-hash `h2`-only variant is retired. Both Operational Format (token generator) and Admin Handle Callback (token verifier) now share one function, one seed set, one output length (12 hex chars).

## Fix 2 — improved outcome vocabulary (IMPLEMENTED, contract-level)

Callback outcomes were widened beyond a single generic "not found" message, per charter:

| Outcome | Meaning |
|---|---|
| `not_found` | No CLEAN row matches the token or recomputed id |
| `ambiguous` | More than one candidate matched — fail closed, no mutate |
| `archived` | Lead exists but is in an archived/legacy tab, not actionable from this card |
| `storage_error` | Sheets read/write itself failed (distinct from a clean "not found") |

Each outcome now maps to a distinct, honest Telegram reply instead of one blanket message — an operator/moderator can now tell a genuine missing lead apart from a transient storage problem.

## Fix 3 — token written before CLEAN append (IMPLEMENTED, contract-level for the deterministic Lead Processor path)

The deterministic Lead Processor is specified to compute and embed `telegram_action_token` **before** the CLEAN `Append` write, closing the write-order gap identified in [CALLBACK-NOT-FOUND-ROOT-CAUSE-v1.md](CALLBACK-NOT-FOUND-ROOT-CAUSE-v1.md) (secondary cause). Where this path has been applied, new rows carry a non-empty `telegram_action_token` at append time rather than relying solely on live recompute.

## Consequence for Клиент A's existing card

Клиент A's card was generated by Format **after** the canonicalization already existed in the token generator, so its embedded button token **already equals** `fnvToken(lead_id)` — the same value the repaired Admin Handle Callback now computes. The card does **not** need to be resent: pressing the existing "processed" button again should resolve correctly against the repaired verifier.
