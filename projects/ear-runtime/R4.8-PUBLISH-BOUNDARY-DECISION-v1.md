## Rationale

1. **R4 scope stays within EAR Publish promotion** — All chartered work addresses consumer-visible snapshot reference, publish metadata, publish lifecycle state, visibility grant, Publish flow gates, and PublishResult emission only. Validate execution, quality certification, snapshot assembly, evidence generation, and consumer program execution remain explicitly out of scope across R4 Charter, Implementation Charter, and R4.7 prohibitions.

2. **R2 boundary preserved** — R4 never reads quarantine as publish target; never generates or mutates Evidence Package (VB-R4-08; R4-CHARTER non-inputs). Evidence lifecycle, validation, and quarantine remain R2 exclusive.

3. **R3 boundary preserved** — R4 consumes validated `SnapshotPackage` read-only; never populates sections or creates `snapshot_id` (VB-R4-04; VB-R4-06). Stage 4 **Publish Assembly** is promotion aggregate composition — distinct from R3 evidence→section assembly (PE-INV-R4-09).

4. **R5 boundary preserved** — R4 consumes `ValidationResult`, `ValidateReport`, and `PublishEligibilityRecommendation` at Stage 2 — never regenerates or substitutes (VB-R4-12). Publish gate verification ≠ EAR Validate (VB-R4-05). Dual HITL: Validate sign-off precondition + Publish approval Stage 3 (VB-R4-02).

5. **Quality ownership clean** — R5 certifies L0–L3; R4 freezes certified level as published claim — no inflation (VB-R4-07). Three semantic stages preserved: candidate / certified / published.

6. **PublishResult disambiguation clean** — PublishResult ≠ ValidationResult ≠ Recommendation ≠ PublishedSnapshot (VB-R4-09/10; PR-INV-R4-01). BLOCKED ≠ Validate FAIL; SUCCESS ≠ quality certification (VB-R4-16/17).

7. **Publish Engine architecture orchestration-only** — R4.7 seven stages verify gates, promote read-only, assign metadata, grant visibility, emit PublishResult — without hidden validation, quality assessment, R3 assembly, acquisition, or consumer intake.

8. **Runtime code aligned** — R4.1–R4.4 model modules contain contracts only; no Publish Engine; R2/R3 validators unchanged from R3.6/R2.4 boundary classifications.

9. **No critical violation** — No code changes required for boundary compliance at design layer. Medium/Low drifts tracked as notes, not blockers.

**PASS WITH NOTES** (not bare **PASS**): Stage 4 vs R3 assembly terminology creep risk (DRIFT-R4-01); Stage 2 naming vs R5 Validate (DRIFT-R4-02); Store metadata write scope (DRIFT-R4-03); combined Store+Publish HITL enforcement (DRIFT-R4-04); in-memory validated path on production (DRIFT-R4-08).

**FAIL** would apply if R4 chartered Validate execution, quality certification, snapshot section assembly, evidence quarantine mutation, replacement of HITL/R5/R3/consumers, or conflation of PublishResult with ValidationResult — **none apply**.
