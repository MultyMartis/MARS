## IV-01 — Snapshot overwrite prevention

### Scenario

Operator or CLI runs mock persist twice with the same `snapshot_id`, `acquisition_id`, and `output_root`.

### Mechanism (code)

1. `snapshot_dir = Path(layout["paths"]["snapshot_dir"])`
2. If `snapshot_dir.exists()` → raise `PersistenceError` with message containing `snapshot_id already exists (immutable store)`
3. Only then `snapshot_dir.mkdir(parents=True, exist_ok=False)`

### Expected outcomes

| Outcome | Expected |
|---------|----------|
| Second call returns / raises | **FAIL CLOSED** — `PersistenceError` |
| Connector wrapper | `validation.valid: false`, error message in `errors` |
| CLI | Non-zero exit when persist validation invalid |
| `metadata.json` content after second call | **Unchanged** from first successful persist |
| `safe-unknown.json` | **Unchanged** |
| `acquisition-log.json` | **Unchanged** |
| New files alongside existing snapshot | **None** |

### R1.9 status

| Evidence type | Result |
|---------------|--------|
| Code review | **PASS** |
| Live second persist | **NOT EXECUTED** (deferred per R1.8E R-01) |

## IV-02 — Directory collision behavior

### Scenario A — Full snapshot directory exists

Same as IV-01. Directory may contain complete three-file set.

**Expected:** Failure at step `exists()` check; **no** `mkdir`, **no** writes.

### Scenario B — Empty snapshot directory exists (orphan)

Prior run created `snapshot_dir` then crashed before all files written (theoretical).

**Expected:**

| Step | Expected |
|------|----------|
| Second persist | **FAIL CLOSED** at `exists()` — treats empty dir as collision |
| Repair | **Not automated** — operator manual cleanup **SAFE UNKNOWN** |

### Scenario C — Parent `acquisition_id` path only

First snapshot under acquisition; second snapshot **different** `snapshot_id`.

**Expected:** **Allowed** — new subdirectory under `snapshots/`.

### Scenario D — Concurrent double persist (race)

Two processes pass `exists()` before either `mkdir`.

**Expected:**

| Process | Expected |
|---------|----------|
| First `mkdir` | Success |
| Second `mkdir` | `FileExistsError` from `exist_ok=False` — **not** mapped to `PersistenceError` today |
| Outcome | **At most one** complete writer; second may raise unhandled exception — **PARTIAL** fail-closed |

### R1.9 status

**PASS WITH NOTES** — single-threaded CLI assumption; race not hardened.

## IV-03 — Metadata overwrite behavior

### Scenario

Attacker or bug attempts re-write of `metadata.json` for existing snapshot via Store API.

### Mechanism (code)

Writer loop:

```text
for filename, payload in (metadata, safe-unknown, acquisition-log):
    target = snapshot_dir / filename
    if target.exists():
        raise PersistenceError(refusing to overwrite)
    target.write_text(...)
```

### Expected outcomes

| Condition | Expected |
|-----------|----------|
| All three files absent | All three created with layout payloads |
| `metadata.json` already exists | **FAIL CLOSED** before write; later files not written in that invocation |
| Partial files from crashed prior run | First existing file in loop order blocks; dir may already exist from earlier step — see IV-02-B |

### Metadata semantic immutability (content)

| Aspect | Expected (R1.8) |
|--------|-----------------|
| `created_at` on re-attempt | **N/A** — re-attempt does not succeed |
| `store_state` mutation in place | **Prevented** by IV-01 / IV-03 |
| External manual edit of JSON | **Out of scope** — Store does not enforce WORM on disk |

### R1.9 status

**PASS** for Store API overwrite prevention (code). **No** filesystem watcher or hash attestation.
