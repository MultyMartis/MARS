# WPilot Pre-Live Hardening Validation v0

**Status:** CORE / PARTIALLY OPERATIONAL / DEV-ONLY.
**Scope:** compact pre-live hardening pass before first real DEV installation of the read-only WPilot MVP.

This validation covers only `projects/wpilot/**`. It does not validate production use, write operations, rollback execution, browser automation, background jobs, autonomous behavior, arbitrary SQL, arbitrary filesystem access, or live WordPress behavior.

## Centralization Summary

Created a central constants layer in `includes/class-wpilot-constants.php` for:

- plugin version and schema version;
- REST namespace;
- option key;
- transient prefix;
- state labels;
- capability string;
- token header names;
- plugin slug and DEV label;
- read response limits;
- JSON content type.

Created `includes/class-wpilot-errors.php` to centralize deterministic refusal/error builders for:

- `AUTH_MISSING`;
- `AUTH_INVALID`;
- `TOKEN_REVOKED`;
- `BRIDGE_DISABLED`;
- `EMERGENCY_DISABLED`;
- `DEV_NOT_CONFIRMED`;
- `SAFE_UNKNOWN`;
- `INVALID_REQUEST`;
- `UNSUPPORTED_OPERATION`;
- `TARGET_NOT_FOUND`.

Created `includes/class-wpilot-environment.php` for deterministic environment gates:

- bridge enabled;
- DEV confirmed;
- emergency-disabled;
- write-disabled;
- environment validity;
- operational readiness.

Created `includes/class-wpilot-request-context.php` for request-scoped metadata extraction:

- request ID;
- UTC timestamp;
- endpoint name;
- auth state;
- bridge state snapshot;
- client IP when safely available;
- capped user-agent capture.

## Refactor Summary

- `metacode-wpilot.php` now loads the central constants and derives legacy global constants from them.
- `WPilot_Settings` now uses centralized option, token, and state constants.
- `WPilot_Auth` now uses centralized token header names, environment gates, and refusal builders.
- `WPilot_REST_Controller` now uses the centralized namespace, plugin slug, request metadata, and response metadata.
- `WPilot_Site_Reader` now uses the centralized page limit and target-not-found refusal.
- `WPilot_Admin_Page` now uses the centralized page slug, capability, namespace display, and environment readiness checks.
- `WPilot_Response` now applies deterministic no-cache JSON headers to plugin-owned responses.

## Operational Risks Reduced

- Duplicated operational literals are reduced in executable plugin code.
- REST namespace ownership is centralized for route registration and admin display.
- Auth and bridge refusals now route through one refusal builder.
- Bridge readiness checks are separated from token validation.
- Request metadata is generated per request without creating a persistent tracking system.
- Response cache behavior is explicit for plugin-owned REST envelopes.
- Admin UI warnings are clearer about DEV-only use, production prohibition, emergency disable state, token rotation, endpoint exposure, and raw content exposure.

## Static Validation Results

**Namespace literal scan:** PARTIALLY OPERATIONAL.

- Executable code now centralizes `wpilot/v1` in `WPilot_Constants::REST_NAMESPACE`.
- Remaining `wpilot/v1` matches are in README/operator documentation examples.

**Accidental write route scan:** OPERATIONAL.

- Static scan found route registrations only in `class-wpilot-rest-controller.php`.
- Registered plugin routes remain `WP_REST_Server::READABLE`.
- No REST route registration for `POST`, `PUT`, `PATCH`, `DELETE`, `CREATABLE`, `EDITABLE`, or `DELETABLE` was found.

**Plaintext token storage scan:** PARTIALLY OPERATIONAL.

- Token plaintext is generated by `WPilot_Settings::generate_token()` and returned to the admin request once.
- Stored token state remains `token_hash` via `wp_hash_password()`.
- Validation did not find a static plaintext token secret in plugin files.
- Live WordPress option storage behavior remains a DEV-install validation item.

**Direct SQL mutation scan:** OPERATIONAL.

- Static scan found no `$wpdb`, `INSERT`, `UPDATE`, `DELETE`, `REPLACE`, or `dbDelta()` usage in the plugin source.

**Filesystem manipulation scan:** OPERATIONAL.

- Static scan found no `file_put_contents`, `fwrite`, `fopen`, `unlink`, `mkdir`, `rmdir`, `rename`, `copy`, `move_uploaded_file`, `chmod`, `chown`, or `touch` usage in the plugin source.

**PHP syntax validation:** SAFE UNKNOWN.

- PHP CLI was not available in the current environment, so `php -l` could not be executed.

## Remaining SAFE UNKNOWN

- SAFE UNKNOWN: first real WordPress DEV installation behavior is not proven by static repo inspection.
- SAFE UNKNOWN: interaction with host security plugins, REST header stripping, cache layers, and reverse proxies is not proven.
- SAFE UNKNOWN: token delivery and operator secret handling cannot be verified without the live DEV procedure.
- SAFE UNKNOWN: raw page content sensitivity depends on the selected DEV pages.
- SAFE UNKNOWN: PHP syntax/runtime compatibility needs validation in an environment with PHP CLI or the target WordPress runtime.

## Remaining Live-Install Risks

- DEV site may accidentally be production-like or contain sensitive content.
- REST endpoint availability may be affected by permalink, security, cache, or host configuration.
- `X-WPilot-Token` may be stripped or transformed by infrastructure.
- Raw `content_raw` exposure is intentional for read-only inspection but must be limited to approved DEV pages.
- Admin token generation still depends on operator copying and storing plaintext safely.
- This pass does not add writes, rollback execution, browser automation, background jobs, autonomous behavior, arbitrary SQL, or arbitrary filesystem/code execution.
