# WPilot DEV Installation Validation Flow v0

**Status:** CORE / PLANNED / DEV-ONLY.
**Scope:** first installable plugin validation flow for a confirmed DEV WordPress site.

This flow defines how the MVP should be installed and validated manually. It is deterministic, minimal, observable, rollback-first, and refusal-first.

## Preconditions

Required before installation:

- Human operator confirms the site is DEV/test.
- Human operator confirms authorization.
- Existing site backup and rollback owner are known outside the plugin.
- WordPress administrator access is available.
- No credentials or tokens are stored in this repository.
- Plugin ZIP is local and intentionally installed by a human administrator.

Abort validation if:

- Site may be production.
- Authorization is unclear.
- WordPress admin access is unavailable.
- Backup/rollback ownership is unknown.
- Security incident is suspected.

## 1. Local ZIP Install Flow

1. Build `metacode-wpilot.zip` from the planned plugin folder.
2. Human administrator opens WordPress admin.
3. Upload ZIP through Plugins -> Add New -> Upload Plugin.
4. Install plugin.
5. Activate plugin.

Expected result:

- Plugin activates without fatal error.
- Plugin admin page appears.
- Bridge remains disabled.
- No REST operation is accepted yet.

Abort if:

- Plugin cannot activate.
- Activation produces PHP fatal error.
- Storage setup fails without visible admin error.
- Bridge is enabled by default.

## 2. Plugin Activation Flow

On activation the plugin should:

- Register plugin version.
- Create required plugin-owned storage or mark setup as blocked.
- Set `enabled = false`.
- Set `dev_confirmed = false`.
- Avoid generating token automatically unless explicitly chosen by admin.
- Avoid registering operational behavior that works while disabled.

Manual checks:

- Admin warning says DEV-only.
- Status screen says disabled.
- Storage status is visible.
- No token is shown unless generated by human action.

## 3. Initial Configuration

Human administrator should:

1. Read DEV-only warning.
2. Confirm site is DEV/test.
3. Enable bridge.
4. Save settings.

Expected result:

- Bridge enabled state is visible.
- DEV confirmation state is visible.
- Audit event records configuration change without secrets.

Abort if:

- Non-admin can configure plugin.
- Settings save without nonce/capability checks.
- DEV confirmation is not explicit.

## 4. Token Generation

Human administrator should:

1. Generate a per-site token.
2. Store it outside the repository using secure operator handling.
3. Confirm token is shown only once.
4. Confirm token can be rotated or revoked.

Expected result:

- Token-authenticated REST calls can be attempted.
- Plaintext token is not visible in logs.
- Token metadata shows created/rotated state.

Abort if:

- Token is stored or logged in plaintext.
- Token cannot be revoked.
- Revoked token still works.

## 5. First API Test

Call the status/site-info endpoint with token authentication.

Expected result:

- Authenticated request succeeds.
- Response includes sanitized plugin/site status.
- Response does not include secrets.
- Audit log records request.

Refusal test:

- Same request without token must fail.
- Same request with invalid token must fail.

Abort if:

- Unauthenticated request succeeds.
- Invalid token succeeds.
- Error response leaks stack traces, paths with secrets, or token values.

## 6. First Read-Only Test

Run read-only endpoints:

- Site info.
- Theme/plugin inventory.
- Pages list.
- Single page read.
- WPBakery map for selected page.

Expected result:

- Data is sanitized.
- No content is mutated.
- WPBakery map reports supported and SAFE UNKNOWN areas.
- Audit logs record read operations.

Abort if:

- Read-only endpoint mutates content or settings.
- Endpoint exposes secrets or unrelated personal data.
- Endpoint allows plugin/theme/core updates.

## 7. First Backup Test

Create a backup for one selected DEV page.

Expected result:

- Backup ID is returned.
- Backup checksum is returned.
- Backup is linked to target page.
- Audit log records backup creation.
- Page content remains unchanged.

Abort if:

- Backup creation changes content.
- Backup target is not the selected page.
- Backup content cannot be restored in principle.
- Backup storage exposes secrets or unrelated data.

## 8. First Scoped Replacement Test

Use a clearly safe DEV page and a unique plain-text occurrence.

Flow:

1. Submit dry validation request.
2. Confirm match count is exactly one.
3. Confirm allowed edit zone.
4. Confirm backup requirement.
5. Human approves execution.
6. Execute scoped replacement.
7. Read page content through WordPress/API.
8. Manually verify frontend.

Expected result:

- Backup exists before mutation.
- Replacement count is exactly one.
- WPBakery structure remains valid enough for MVP.
- Audit log records lifecycle.
- Response includes backup ID and checksums.

Abort if:

- Match count is zero or multiple.
- Target is in forbidden WPBakery/HTML/attribute zone.
- Backup fails.
- Expected checksum mismatches.
- Post-write validation fails.
- Manual frontend verification fails.

## 9. First Rollback Test

Rollback the same page using the plugin-created backup.

Flow:

1. Submit rollback request with backup ID.
2. Authenticate request.
3. Validate backup belongs to target page.
4. Restore through WordPress APIs.
5. Generate post-rollback checksum.
6. Manually verify frontend.

Expected result:

- Original text is restored.
- Backup ownership is verified.
- Rollback audit event is written.
- No unrelated page is modified.

Abort if:

- Backup ID is unknown.
- Backup target mismatch.
- Current content cannot be read.
- WordPress API returns error.
- Post-rollback verification fails.

## 10. Required Manual Verification

Manual verification is required after:

- Plugin activation.
- Bridge enablement.
- Token generation.
- Read-only inspection.
- Backup creation.
- Scoped replacement.
- Rollback.
- Token revocation or bridge disablement.

Manual verification should record:

- Target page.
- Operation ID.
- Backup ID.
- Before/after visible state.
- Rollback status.
- SAFE UNKNOWN.
- SECURITY RISK.

## Closeout

After validation:

- Review audit log.
- Disable bridge or revoke token unless further DEV testing is planned.
- Confirm no secrets were stored in repo.
- Record remaining SAFE UNKNOWN.
- Record security risks.

## Validation Philosophy

Prefer:

- Deterministic checks.
- Minimal endpoint surface.
- Observable logs.
- Rollback-first writes.
- Refusal-first behavior.
- Manual verification.

Reject:

- Smart autonomous editing.
- Hidden recovery.
- Automatic repair.
- Browser automation.
- Deployment/update behavior.
- Unbounded retries.
