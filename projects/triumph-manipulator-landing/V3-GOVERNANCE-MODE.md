# Triumph Manipulator Landing V3 — Governance Mode

## 1. Purpose

This file defines the operational governance mode for the V3 Forge battle test.

The goal is **deployable governance**: enough discipline to prevent drift and trust inflation, without turning the rebuild into checklist theater or cognitive overload.

## 2. Default operational mode

The default V3 mode is **adaptive standard mode**.

Adaptive standard mode means:

- Use Forge doctrine as the active operating discipline.
- Scale review depth to source ambiguity, implementation risk, and production consequence.
- Keep findings evidence-based and source-linked.
- Preserve operational readability over exhaustive theory coverage.
- Prefer concise findings over broad governance recitation.

## 3. Critical mode activation

Critical mode activates when any of the following appear:

- V1 source authority is ambiguous, missing, contradictory, or insufficient for a section.
- A reconstruction choice would materially change hierarchy, strategic intent, section meaning, or CTA priority.
- Responsive collapse risks breaking composition, trust hierarchy, scanning rhythm, or conversion continuity.
- Implementation decisions risk future-edit fragility, unreadable structure, or patch accumulation.
- QA evidence is weak but confidence language is drifting upward.
- V2 implementation residue begins influencing V3 structure, CSS, layout, or local fixes.

Critical mode requires explicit stop-and-review behavior before continuing the affected scope.

## 4. Lightweight mode allowance

Lightweight mode is allowed only when:

- The source is clear.
- The implementation choice is local and reversible.
- The risk is low.
- No source authority conflict exists.
- No hidden approximation is being introduced.
- The review can remain honest with compact evidence.

Lightweight mode is not a permission to skip source lineage, approximation disclosure, responsive checks, or QA honesty.

## 5. SAFE UNKNOWN mandatory conditions

SAFE UNKNOWN is mandatory when:

- The exact V1 source pack boundary is not fully enumerated.
- Text, hierarchy, layout intent, image origin, responsive behavior, or asset authority cannot be proven from approved sources.
- V1 and secondary governance lessons conflict.
- V2 appears to answer a question that V1 does not answer.
- QA evidence is incomplete or viewport/device coverage is unverified.
- Production readiness is inferred from visual similarity or build success alone.

## 6. HITL mandatory conditions

Human-in-the-loop review is mandatory when:

- A decision changes section meaning, copy, CTA priority, proof hierarchy, or business strategy.
- A missing source requires interpretation beyond conservative reconstruction.
- V2 lesson material is proposed as a constraint on V3 implementation.
- A waiver is needed for fidelity, responsiveness, accessibility, production readiness, or maintainability.
- A failure condition may be triggered.
- The operator must approve a source authority expansion.

## 7. Review scaling logic

Review scales by risk, not by doctrine inventory.

Use deeper review for:

- High-visibility sections.
- Strategic hierarchy and CTA zones.
- Complex responsive collapse.
- Source ambiguity.
- Cross-section dependencies.
- Production-readiness and future-edit risk.

Use compact review for:

- Clear source-to-build transfers.
- Low-risk local refinements.
- Repeated patterns already validated in the same V3 cycle.

## 8. Compression expectations

Governance output must remain readable under production pressure.

Reports should compress to:

- Decision made.
- Source basis.
- Approximation, if any.
- Risk level.
- QA evidence.
- SAFE UNKNOWN or HITL need.

Long-form doctrine may be cited when needed, but V3 must prove that Forge can operate as deployable discipline, not as maximum-documentation volume.
