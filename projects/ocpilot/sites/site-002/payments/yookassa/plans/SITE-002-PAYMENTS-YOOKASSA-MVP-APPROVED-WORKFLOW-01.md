# SITE-002 — канонический MVP workflow оплаты (одобрение + ЛК + auto-email)

**Document id:** SITE-002-PAYMENTS-YOOKASSA-MVP-APPROVED-WORKFLOW-01  
**Date:** 2026-09-09  
**Status:** design summary. **No implementation.**  
**Correction parent:** [SITE-002-PAYMENTS-YOOKASSA-MVP-LK-AUTO-EMAIL-CORRECTION-01.md](../decisions/SITE-002-PAYMENTS-YOOKASSA-MVP-LK-AUTO-EMAIL-CORRECTION-01.md)  
**Strategy:** `payment_links_first_api_manager_workflow_hybrid_later`

Формула MVP:

**одобрение менеджера внутри сайта + блок оплаты в существующем ЛК + автоматическое письмо со ссылкой YooKassa**

---

## 1. MVP workflow diagram

```
клиент создаёт заявку/заказ
        |
        v
заявка/заказ существует в системе сайта
        |
        v
менеджер проверяет состав, цену, наличие, доставку, плательщика
        |
        +-- нет --> отказ / уточнение (без ссылки, без письма оплаты)
        |
        v
менеджер одобряет оплату внутри сайта / admin
        |
        v
сайт создаёт или прикрепляет ссылку YooKassa
        |
        v
сайт сохраняет ссылку и статус оплаты к заявке/заказу
        |
        v
сайт автоматически шлёт клиенту письмо (сводка, документы, ссылка)
        |
        v
клиент видит тот же payment block в ЛК
        |
        v
клиент платит по ссылке  ИЛИ  обычным безналом
        |
        v
MVP: сверка оплаты может быть ручной (кабинет YooKassa)
        |
        v
позже: webhook/API обновляет статус оплаты автоматически
```

Checkout-first, официальный модуль OC как шаг 1, оплата до одобрения — **вне** этой схемы.

---

## 2. Manager actions

Менеджер:

1. Открывает заявку/заказ в сайте / admin.
2. Проверяет комплектацию, цену, наличие, доставку, плательщика, НДС/чековый подход (как подтвердит учёт).
3. При необходимости выпускает КП / обычный счёт (безнал остаётся).
4. **Одобряет оплату** внутри workflow сайта (не в почтовом клиенте).
5. Не собирает и не отправляет платёжное письмо.
6. После оплаты (MVP): сверяет кабинет YooKassa / отмечает сверку по процедуре, пока нет webhook — **сверка**, не «отправить ссылку письмом».

---

## 3. Site automatic actions

После одобрения сайт:

1. Создаёт ссылку YooKassa **или** прикрепляет уже созданную ссылку к заявке/заказу.
2. Сохраняет поля ссылки и статус оплаты против заявки/заказа.
3. Отправляет клиенту **автоматическое** письмо.
4. Показывает тот же блок в ЛК (список + деталь).
5. Не считает `return_url` фактом оплаты.
6. Не мапит paid → OpenCart status 5 «Сделка завершена».
7. Не включает универсальный checkout.

---

## 4. Client email contents

Автописьмо после одобрения должно содержать (русский, без leftover OC):

- номер / идентификатор заявки или заказа;
- краткую сводку состава и **сумму к оплате онлайн** (если доставка вне ссылки — явно сказать);
- ссылки на документы / КП / счёт, **если они есть**;
- **ссылку YooKassa**;
- статус оплаты на момент письма (обычно «ожидает оплаты»);
- напоминание, что те же данные есть в **ЛК**;
- контакт менеджера;
- что обычный безнал по счёту по-прежнему возможен, если так ведут эту заявку.

Не заменяет ЛК. Не является истиной оплаты после клика «вернуться в магазин».

---

## 5. ЛК payment block contents

В существующем ЛК (обязательная поверхность MVP):

- заявка/заказ в списке;
- деталь заявки/заказа;
- состояние «одобрено к оплате» (когда применимо);
- сумма;
- документы / КП / счёт, если доступны;
- ссылка YooKassa (пока не оплачено / пока ссылка действительна);
- статус оплаты (отдельно от статуса заявки и отгрузки);
- контакт менеджера;
- ясный русский текст, мобильная читаемость;
- без сломанного default OpenCart UX как единственного экрана оплаты.

Детали правок: [SITE-002-CUSTOMER-ACCOUNT-UX-ORDER-PAYMENT-FIX-PLAN-01.md](../backlog/SITE-002-CUSTOMER-ACCOUNT-UX-ORDER-PAYMENT-FIX-PLAN-01.md).

## 6. Required order/request data

Минимум, без которого нельзя одобрять онлайн-оплату:

| Поле | Зачем |
|------|--------|
| Идентификатор заявки/заказа / КП / счёта | Привязка ссылки, письма, ЛК |
| Состав / коммерческая ссылка | Что одобрено |
| Финальная сумма этой оплаты | Ссылка и чек |
| Плательщик | Чек, B2B |
| Контакт (email, при необходимости телефон) | Auto-email и чек |
| Решение по доставке в этой оплате | Сумма и чек |
| Подход к НДС / чеку | До live — подтверждение учёта |
| Кто одобрил и когда | Аудит |

---

## 7. Required payment-link fields

Хранить против заявки/заказа (не только в письме менеджера):

| Поле | Зачем |
|------|--------|
| URL ссылки YooKassa | ЛК и письмо |
| Идентификатор платежа (если уже есть) | Сверка / позже API |
| Сумма ссылки | Совпадение с одобренным |
| Статус оплаты | Отдельно от OC order status |
| Срок / действительность (если есть) | Не показывать мёртвую ссылку как актуальную |
| Кто/когда прикрепил или создал | Аудит |
| Признак «письмо отправлено» | Не слать дубли бесконтрольно |

`return_url` — только UX возврата, не статус.

---

## 8. Manual parts in MVP

Допускается вручную:

- сверка оплаты в кабинете YooKassa;
- создание ссылки в кабинете **с последующим attach на сайте**, если API-create ещё не в этапе;
- обычный безнал / счёт как альтернатива.

Не допускается как модель MVP:

- менеджер шлёт платёжное письмо вручную вместо сайта;
- оплата только по email без блока в ЛК;
- доверие success-page / `return_url`.

---

## 9. Later webhook/API upgrade

- API создаёт платежи на одобренную сумму.
- Webhook/API обновляет **статус оплаты**.
- Идемпотентность дублей/задержек.
- Три линии статусов: заказ/заявка, оплата, отгрузка/исполнение (+ отдельно чек).
- Не истина: `return_url`. Не маппинг paid → status 5.

Это **не** MVP-блокер для формулы «одобрение + ЛК + auto-email».

## 10. Later ЛК UX improvement

После/параллельно MVP:

- logged-in аудит тестовым аккаунтом;
- убрать leftover OC (wishlist, rewards, recurring, пустые downloads как «кабинет счетов»);
- polish списка/детали, мобильная вёрстка, копирайт.

Полный polish **не** откладывает обязательность payment block в ЛК. Исторический guest-HTTP: `SITE-002-CUSTOMER-ACCOUNT-UX-ORDER-PAYMENT-READONLY-01.md`.
