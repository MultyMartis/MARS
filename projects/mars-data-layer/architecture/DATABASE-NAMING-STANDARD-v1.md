# Database Naming Standard v1

**Document:** `DATABASE-NAMING-STANDARD-v1`  
**project_id:** `mars-data-layer`  
**Date:** 2026-09-03

---

## 1. Database

| Object | Name |
|--------|------|
| Application database | `mars` |

One database for Hybrid B + D-lite V1. Separate databases only when Phase 10 evidence requires.

---

## 2. Schemas

| Pattern | Examples |
|---------|----------|
| Platform | `mars_core`, optional `mars_shared` |
| Applications | `app_<domain>` — **prefix `app_` mandatory** |

Examples:

- `app_iseo_sales`
- `app_seo_content`

Future bots: `app_<short_snake_domain>`.

---

## 3. Table names

**Standard: `snake_case` plural.**

Justification:

- Aligns with common PostgreSQL/n8n operational reading (“many rows”).
- Avoids mixed singular/plural drift across bots.
- Status/history tables remain plural (`events`, `jobs`, `errors`).

Examples: `leads`, `jobs`, `events`, `idempotency_keys`, `audit_log` (exception: `audit_log` as conventional singular collective — prefer `audit_logs` for new tables).

**New tables:** prefer strict plural (`audit_logs`).

---

## 4. Primary keys

**Default for new internal rows:** `BIGINT GENERATED BY DEFAULT AS IDENTITY` (or `GENERATED ALWAYS AS IDENTITY`).

**Use UUID (`uuid`, prefer `gen_random_uuid()`)** when:

- the identifier must be minted **outside** the database before insert;
- cross-system merge / offline clients need non-colliding ids;
- public opaque tokens must not leak sequence cardinality.

**External stable IDs** (Gmail message id, Telegram update id, Sheets row id during shadow) remain **separate unique columns**, not necessarily the primary key:

```text
id              -- internal PK
gmail_message_id -- UNIQUE NULLS DISTINCT / unique where present
```

Do **not** blindly UUID every table.

---

## 5. Timestamps

| Column | Type | Semantics |
|--------|------|-----------|
| `created_at` | `timestamptz` | Insert time |
| `updated_at` | `timestamptz` | Last update |
| `available_at`, `lease_until`, … | `timestamptz` | Scheduling |

**Standard:** all timestamps are **timezone-aware** (`timestamptz`). Store UTC; display in operator TZ (e.g. Europe/Moscow) at the edge.

Avoid `timestamp without time zone` for new columns.

---

## 6. Status columns

**V1 strategy:** `text` + `CHECK` constraint (or domain) listing allowed values.

Justification vs PG enums:

- Expand/contract migrations are simpler (add value = constraint replace).
- Avoids painful enum rewrite during early bot evolution.
- Application/Toolkit still validates the same closed set.

Example values for jobs: `pending`, `running`, `retry`, `completed`, `dead`, `cancelled`.

Document allowed values next to the table in migration comments.

---

## 7. Foreign keys

- Name: `fk_<table>_<referenced_table>[_<column>]` when disambiguation needed.
- Prefer explicit `ON DELETE`/`ON UPDATE` (usually `RESTRICT`/`NO ACTION` for business; `CASCADE` only when child is pure owned detail).
- Cross-schema FKs allowed sparingly (`app_*` → `mars_core`) — avoid chatty cross-app FKs.

---

## 8. JSONB use

Allowed for **flexible payload/metadata** only:

- provider raw payloads;
- non-query-critical attributes;
- versioned envelope blobs.

Not allowed as a substitute for core relational fields that drive filtering, uniqueness, or joins (`status`, `correlation_id`, emails, foreign keys).

---

## 9. Index naming

Pattern:

```text
idx_<table>_<columns_snake>
uq_<table>_<columns_snake>     -- unique indexes when not named as constraints
```

Keep names ≤ 63 chars; abbreviate middle segments if needed.

---

## 10. Constraint naming

| Type | Pattern |
|------|---------|
| Primary key | `pk_<table>` |
| Unique | `uq_<table>_<cols>` |
| Check | `ck_<table>_<purpose>` |
| Foreign key | `fk_<table>_<ref>` |

---

## 11. Column conventions

- Boolean: `is_` / `has_` prefix when clarity helps (`is_active`).
- Money: explicit currency column if needed; never float.
- Soft delete: only if product requires; prefer explicit status otherwise.
