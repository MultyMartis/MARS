## 1. Visual reconciliation — concept (inside Website Factory)

**Visual reconciliation** is a **human-supervised** step: a disciplined comparison between **approved visual source** (exports, implementation pack notes) and **built UI** that focuses on **what draws the eye**, **how dense the section feels**, and **how emphasis is distributed** — without claiming mathematical pixel equality.

| Layer | What it guards | Primary question |
|-------|----------------|------------------|
| **Semantic QA** | Meaning, copy, entity counts, CTA *roles*, section order, version purity | “Did we ship the **right story** and **right content**?” |
| **Responsive QA** | Breakpoint survivability, overflow, tap targets, layout collapse *mechanics* | “Does the layout **survive** widths without breaking?” |
| **Visual reconciliation** | Hierarchy, dominance, rhythm, grouping, balance, perceived density, focal flow | “Does the build **read like** the source **as a design** — not only as a schema?” |

**Why semantics alone are insufficient:** Correct headings, landmarks, and copy can still produce a **flattened** or **wrong-weight** page: equalized cards, hero CTAs visually weaker than secondary actions, trust blocks that **overtake** the hero focal path, spacing that inflates until the narrative feels like a list of boxes. Semantic QA does not mandate *relative visual prominence*; visual reconciliation does — **as a governance read**, not as an automated judge.

**Difference from responsive QA:** Responsive QA asks whether regions **fit and function** at key widths. Visual reconciliation asks whether **emphasis and flow** remain **credible** at those widths — e.g. accidental **equalization** on tablet, or **focal collapse** when stacks reflow.

### 1.1 Foundation vs screen-local intent — governance rule

**Foundation contamination bias** is the drift class where **semantic QA** can **pass** and structure can remain **stable**, but **visual intent** is wrong because **global foundation defaults** (site-wide theme, inherited surfaces, styling carried from **previous sections** or **neighbor screens**) **overpower** the chartered **screen-local** role.

**Governance rule (interpretation only):** When the canonical screen source clearly indicates a visual role that differs from pipeline or site-wide defaults, **screen intent overrides foundation defaults.** This rule describes **human-supervised** token and treatment choice against chartered exports and packs — **not** a runtime theme switcher, **not** adaptive styling AI, **not** autonomous visual redesign.

**Vocabulary (full definitions, symptoms, mitigation):** [visual-drift-taxonomy.md §D](visual-drift-taxonomy.md).

**Critical clarification:** A coherent **global** design system does **not** guarantee correct **per-screen** interpretation; “consistent with the site” can still violate **this screen’s** chartered light band, card treatment, or contrast reset.

## 2. Visual reading dimensions (practical, implementation-oriented)

Use these as **review axes** when comparing source screen to build. They are **checklist dimensions**, not instrumental measurements.

| Dimension | What to read for | Implementation hooks (examples) |
|-----------|------------------|-----------------------------------|
| **Hierarchy** | What is primary vs secondary text; headline–subhead–body ladder | Type scale, weight, color contrast, line length, H-tag alignment with *visual* size |
| **Dominance** | Which element should win attention in the section | Size, contrast, isolation, motion (if any), “only primary CTA” styling |
| **Rhythm / cadence** | Vertical/horizontal beat of sections and blocks; inter-screen spacing as narrative pacing | Spacing tokens, repeat intervals, grid gaps vs design pack; [canonical-vertical-cadence-system.md](canonical-vertical-cadence-system.md), [cadence-tier-model.md](cadence-tier-model.md), [typography-rhythm-governance.md](typography-rhythm-governance.md), [vertical-rhythm-governance.md](vertical-rhythm-governance.md) |
| **Grouping** | What belongs in one visual cluster vs separate | Background bands, borders, cards, whitespace gutters |
| **Balance** | Left/right or top/bottom visual weight | Asymmetry vs centered stacks; media vs copy weight |
| **Spacing perception** | Airiness vs compression — *felt* density | Margin tiers, paragraph spacing, list density |
| **Visual density** | How much competes in one viewport band | Chips, badges, multi-column grids, icon rows |
| **CTA emphasis** | Primary vs secondary vs tertiary actions | Button styles, placement above/below fold in section |
| **Trust positioning** | Where proof sits relative to conversion narrative | Above/below fold, adjacency to claim, strip vs card |
| **Icon semantics / rhythm** | Whether icons carry the right meaning, family weight, and optical beat for their role | FA style choice, icon column width, baseline, icon/text gap; see [font-awesome-governance-layer.md](font-awesome-governance-layer.md) |
| **Section emphasis** | Hero vs supporting vs footer — narrative role | Section min-height, contrast, hero-only treatments |
| **Asymmetry** | Deliberate uneven layouts vs accidental drift | Grid proportions, image bleed, offset stacks |
| **Composition flow** | Path eye follows (Z-pattern, F-pattern, single focal) | Column order, imagery direction, CTA alignment |
| **Foundation vs screen-local role** | Whether **this** export is a light island, dark band, contrast reset, or inherits a global chrome — vs accidental **inheritance** from globals | Surface/background tier, card framing, “breathing room” band vs continued dark frame; see drift: **foundation contamination bias** ([taxonomy §D](visual-drift-taxonomy.md)) |

## 4. Visual validation workflow (lightweight)

For a **screen slice** or `block_id`-scoped pass, **validation order** should follow:

1. **Screen** — Anchor to exact source artifact(s) in the active design path (charter per [semantic source lock](../../agents/mars-forge/semantic-source-lock.md) §1).  
2. **Visual reading** — Before or while extracting semantics, note intended **hierarchy, focal path, density, CTA dominance, trust placement**, and **screen-local surface role** (light vs dark band, card framing, contrast vs neighbors) — short bullet read, optional in REPORT.  
3. **Implementation** — Forge phases through interaction as applicable ([workflow](../../agents/mars-forge/workflow.md)).  
4. **Semantic QA** — Meaning, copy, entities, CTA roles, version lock (semantic source lock §6).  
5. **Visual reconciliation** — Human-supervised read: compare **visual intent** between source and build using §2 dimensions and drift taxonomy.  
6. **Responsive QA** — Final mechanical spot-check at agreed widths **after** visual reconciliation, so fixes target **both** survival and **emphasis** at breakpoints.  
7. **Freeze** — Only after reconciliation + responsive QA pass or explicit deferrals recorded.

**Rule:** **Visual reconciliation happens before freeze** — it is **not** optional “polish after release.” Deferrals are allowed only as **documented** partials (see §6 in checklist).

**Relation to Forge phases:** Responsive work still occurs **during** implementation (Forge phase 4). The **workflow** above is the **validation closure** order for the slice: a final responsive QA pass **after** visual reconciliation catches “survives but wrong emphasis” gaps.

## 5. Visual observation format (reporting)

Use a consistent block in REPORT (Forge / frontend validation) so findings are auditable and comparable across sessions.

```text
VISUAL FINDINGS — <section or block_id> — <source ref e.g. design/v2/03.png>

Observed vs source (human read):
- Hierarchy: <e.g. primary headline reads weaker than supporting line>
- Dominance / CTA: <e.g. secondary link rivals primary button>
- Density: <e.g. stack reads heavier than source; icon row crowded>
 Rhythm / spacing: <e.g. vertical gaps larger than adjacent sections; rhythm feels “stretched”>
- Grouping: <e.g. trust cluster visually merges with hero>
- Balance / asymmetry: <e.g. centered stack where source is weighted left>
- Trust / proof placement: <e.g. strip draws eye before hero CTA path>
- **Foundation / screen-local role:** <e.g. dark global frame overpowering chartered light surface — drift: foundation contamination bias>
- Focal / flow: <e.g. competing focal points; eye drops to footer prematurely>

Disposition: PASS | PARTIAL (deferrals listed) | FAIL
Evidence: <paths: screenshot optional, URLs, viewport notes — tooling not required>
```

**Honest scope:** Observations are **qualitative**. They do not require pixel diff or AI vision; they require a **named discrepancy** and **disposition**.

## 6. Frontend agent implications

The **frontend agent** (Forge overlay on Gulp foundation) should:

- **Interpret visual intent** from the approved source and implementation pack — not only translate labels into tags.  
- **Read screen-local visual role** first for the chartered slice (**surface**, **card/frame**, **hierarchy mood**, **contrast vs neighbors**) before reusing **global** or **previous-section** tokens.  
- **Preserve hierarchy and emphasis** when choosing type scale, spacing tier, and component variants.  
- **Distinguish global consistency from local screen intent:** cross-page consistency is **not** sufficient when the export defines an **exception** (e.g. light composition on a predominantly dark site — documentation lesson: Triumph V2 Screen 02).  
- **Avoid blind inheritance** of prior section CTA, trust, typography mood, or rhythm when the source implies a **reset** or **different band**.  
- **Avoid accidental visual normalization** (making siblings **too equal** in size/contrast/spacing when the source is deliberately uneven).  
- **Prefer SAFE UNKNOWN** when the export does not resolve emphasis or local mood (see §7).  
- When screen intent **clearly** contradicts foundation defaults, apply the **screen-first** read and **document** the override in REPORT — **without** inventing new layout or unapproved creative redesign.

The agent should **not**:

- Invent a **new creative layout** “for conversion” absent from governance-approved sources.  
- **Default** to site-wide or previous-section styling **without** checking **this** screen’s chartered visual role — that path risks **foundation contamination bias** ([taxonomy §D](visual-drift-taxonomy.md)).  
- Claim **pixel-perfect** match or “objective” visual scoring.  
- Replace human **visual reconciliation** with autonomous judgment.  
- Implement **runtime theming**, **adaptive** style engines, or **automatic** cross-screen visual adaptation — out of scope for Forge governance.

## 7. SAFE UNKNOWN — visual reconciliation

Stop confident implementation or PASS when **visual role** cannot be established from chartered inputs:

### 7.1 Validation prompts — foundation contamination bias

Use these **during** visual reconciliation when global defaults might hide screen-local intent:

- Is the section **visually behaving like its source** (surface, cards, hierarchy mood), not merely semantically correct?
- Did **global theme** or **site chrome** **overpower** chartered screen intent?
- Does this screen **intentionally break** rhythm or contrast vs the previous section — and does the build **preserve** that break?
- Is **local composition** unintentionally **subordinate** to **inherited** styling (globals read louder than the export)?
- Are **neighboring sections** or **prior screens** **visually leaking** into this band (tokens, proof styling, CTA tier)?

If answers cannot be established from inputs → **SAFE UNKNOWN**, not a silent global default.

### 7.2 SAFE UNKNOWN table

| Situation | Why it is UNKNOWN |
|----------|---------------------|
| **Unclear hierarchy in export** | Ambiguous scale/contrast; cannot tell primary from secondary |
| **Missing mobile export** | Breakpoint emphasis cannot be chartered; defer responsive reconciliation |
| **Ambiguous density** | Cropped export, low resolution, or overlapping layers hide spacing intent |
| **Unreadable text** | Illegible copy in raster source — semantic lock also blocks guessing |
| **Conflicting visual exports** | Two “approved” screens disagree on emphasis for the same section |
| **Visual role unclear** | Cannot tell if block is hero focal, supporting, or trust without HITL |
| **No local screen export / unclear charter** | Cannot anchor **screen-local** surface role; foundation default would be a guess |
| **Unclear intended mood** | Cannot tell light vs dark intent, editorial vs campaign tone, or contrast reset vs continuity |
| **Inconsistent exports for same section** | Multiple breakpoints or revisions disagree — which governs **local** role is unresolved |
| **Multiple competing foundations** | Pack + globals + prior implementation disagree; no single chartered precedence |

**Action:** Record **SAFE UNKNOWN** in REPORT with what would resolve it (e.g. named breakpoint export, annotated hierarchy note in implementation pack, explicit pack rule for light-vs-dark **band ownership**, HITL decision).
